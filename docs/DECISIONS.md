# Decisions

One line each, newest at the bottom.

- 2026-11-16 — Pinned TypeScript 6.0.3, not 7.0.2: `@nestjs/swagger`, `typescript-eslint` and `@thallesp/nestjs-better-auth` peer ranges stop at TS 6.
- 2026-11-16 — Pinned Prisma 7.10.1, not the `latest` tag 8.0.0-rc.33: 8 is a release candidate and Better Auth's Prisma adapter does not support it yet.
- 2026-11-16 — Pinned ioredis 5.11.1, not 6.0.0: 5.x is inside BullMQ 6's peer range and has a long track record; 6.0 is a new major.
- 2026-11-16 — Every package is ESM (`"type": "module"`, `nodenext`); NestJS 12 ships ESM-only.
- 2026-11-16 — NestJS dependencies are injected by explicit token (`@Inject(X)`), so no code relies on emitted decorator metadata.
- 2026-11-16 — Better Auth is mounted directly on Express at `/v1/auth` with `toNodeHandler`, ahead of the JSON parser, instead of through a third-party Nest wrapper.
- 2026-11-16 — The Better Auth organization plugin is used only for the session's active organization (`/v1/auth/organization/set-active`), with its `member` model mapped to `OrganizationMembership`. Its other endpoints return 404; organizations, roles and invitations go through DatoFlow's API so the role enum, hashed tokens, 7-day expiry and audit rules hold.
- 2026-11-16 — The web app proxies `/v1/*` to the API through a route handler (not a `rewrites()` entry, which is fixed at build time), so browser, cookies and API share one origin, SameSite=Lax cookies work without CORS, and `API_URL` is read at runtime.
- 2026-11-16 — Session cookies get `Secure` when `APP_URL` is https. Plain-http localhost cannot hold `__Secure-` cookies reliably, so local dev and CI run without it; production is https.
- 2026-11-16 — Auth events are written to the audit log of every organization the person belongs to; a person with no membership yet (sign-up) is only in the request log, since `AuditLog.organizationId` is NOT NULL.
- 2026-11-16 — Better Auth's built-in rate limiter is off; one Redis fixed-window limiter covers auth (5/min per IP on the credential and email-sending endpoints: sign-in, sign-up, reset, verify), the API (300/min per user) and password resets (5/hour per email). Reading the session, signing out and switching workspace are not counted, or normal navigation would trip the limit.
- 2026-11-16 — Tenant isolation runs as a NOLOGIN role `datoflow_app` (`SET LOCAL ROLE` per transaction) that RLS applies to. System work (membership lookup, org creation, accepting an invitation by token) runs as the table owner, which RLS does not apply to.
- 2026-11-16 — `AuditLog` is append-only by trigger: UPDATE always fails, DELETE only inside the future 30-day organization purge (`app.audit_purge = 'on'`).
- 2026-11-16 — A seat is a member or an open invitation, so inviting cannot overbook the plan's user limit. A new invitation to the same address revokes the old open one.
- 2026-11-16 — An invitation that cannot be accepted returns 409 `INVITATION_INVALID` with `reason` (EXPIRED, USED, REVOKED, EMAIL_MISMATCH). The web shows "Ask for a new invite".
- 2026-11-16 — UF-4 "inviter notified" is an email in Phase 1; the in-app notification follows with NOT-01 in Phase 3.
- 2026-11-16 — Listing members follows the API table (Admin minimum) for now; a lighter assignee list for Managers and Reps comes with tasks in Phase 3 if needed.
- 2026-11-16 — ORG-03 resend and revoke are `POST …/invitations/:id/resend` and `POST …/invitations/:id/revoke`; an invitation preview for the accept screen is `GET /v1/invitations/:token`. The API table names neither, but ORG-03 and UF-4 need them.
- 2026-11-16 — Postgres and Redis publish no host ports in the local Compose file. Nothing outside the Compose network needs them, and another local Postgres often holds 5432.
- 2026-11-16 — Minimum password length is 10 characters.
- 2026-11-16 — Display type falls back to Anton (Google Fonts) because no licensed PP Neue Corp Compact files exist in the repo; switching is a change to `apps/web/src/app/fonts.ts`.
- 2026-11-16 — Display headings are uppercase. That follows Caldera's oversized display headline; unslop's "no uppercase labels" rule yields to the product's own brand.
- 2026-11-16 — Local Compose sends email through SMTP to Mailpit (not the console adapter), so verification and invitation links can be clicked at http://localhost:8025. `.env.example` keeps `console` for running the API outside Docker.
- 2026-11-16 — pnpm 12 blocks dependency install scripts by default. Prisma's are allowed; the optional native extras (`msgpackr-extract`, `ssh2`, `cpu-features`, `protobufjs`, `@scarf/scarf`) are denied, which keeps ARM builds free of a compiler toolchain.
- 2026-11-16 — Integration tests run against the compiled API (`apps/api/dist`), so the code under test is what ships.
- 2026-11-16 — Phase 1 gate passed on GitHub Actions (CI and E2E) before Phase 2 work started beyond planning and pure domain code.
- 2026-11-16 — The sample workspace (ORG-04) is seeded into each new organization, on by default with an opt-out on the create form, rather than living in a separate workspace. "Delete sample data" removes it in one click.
- 2026-11-16 — Sample reps are real `User` rows with unroutable `@sample.datoflow.invalid` addresses and no password, so they can own leads and appear on the board. Their memberships carry `isSample` and never count as seats.
- 2026-11-16 — The 2 sample workflows of ORG-04 are added in Phase 4, when the workflow tables exist.
- 2026-11-16 — Sample leads write no outbox events, so they never trigger automation on their own.
- 2026-11-16 — Sample deal values are stored in US dollar terms and scaled by a rough rate for the workspace currency when seeded. Only sample data uses those rates.
- 2026-11-16 — The `OutboxEvent` table and its writes (`lead.created`, `lead.stage_changed`, `lead.assigned`) arrive in Phase 2, in the same transaction as each change. The publisher follows in Phase 4. A new lead with an owner emits only `lead.created`, with the owner in its payload.
- 2026-11-16 — Organizations get a `country` (ISO 3166-1 alpha-2, default LK) for E.164 phone normalisation (LEAD-02). The data model table names no such field, but LEAD-02 needs the org's default country.
- 2026-11-16 — Activity that restarts the stage SLA clock: creation, stage change, reassignment and notes (touches join in Phase 3). Editing a field is logged on the timeline but is not follow-up.
- 2026-11-16 — Stuck-by-SLA is stored as `Lead.slaDueAt` (last activity plus stage SLA, null when closed), so the stuck filter is an indexed comparison. Changing a stage's SLA recomputes it for the leads in that stage. The overdue-next-step half of "stuck" arrives with tasks in Phase 3.
- 2026-11-16 — One pipeline per organization; `POST …/pipelines` is not built, since multiple pipelines (PIPE-04) is a Could.
- 2026-11-16 — A pipeline has exactly one Won and one Lost stage and at least one open stage, at most 12 in all. A stage with leads cannot be removed or switch between open and closed (PIPE-01).
- 2026-11-16 — "Won requires a deal value" is an org setting, on by default (PIPE-03).
- 2026-11-16 — A new lead belongs to whoever creates it unless they choose otherwise. Sales Reps may leave a lead in the pool but cannot assign it to anyone else.
- 2026-11-16 — Listing archived leads needs the archive capability (Owner, Admin, Sales Manager).
- 2026-11-16 — Saved lead filters and the chosen view live on `OrganizationMembership.preferences` (`GET/PUT …/me/preferences`), so they follow the user across devices (LEAD-05).
- 2026-11-16 — `GET …/assignees` lists members with names for any member, so the board and owner pickers work for every role. Emails stay on the Admin-only members list.
- 2026-11-16 — Loss reasons are replaced as a list (`PUT …/loss-reasons`). A reason that leads use is retired (inactive) instead of deleted.
- 2026-11-16 — Date filters use calendar days in the organization's timezone.
- 2026-11-16 — Duplicate detection never pairs sample and real leads, and a lead page only links duplicates the viewer may open.
- 2026-11-16 — Board keyboard moves use their own model (Space to pick up, arrows between stages, Space to drop, Escape to cancel, with live announcements). dnd-kit handles pointer and touch dragging only, because its keyboard sensor moves by pixels, not by stage.
- 2026-11-16 — On the leads page, search and "Stuck only" stay visible and the other filters fold behind a "Filters" button with a count, so the board starts above the fold on desktop and phone.
- 2026-11-16 — `@datoflow/web#typecheck` waits for `@datoflow/web#build` in Turbo, because both write `.next/types`.
- 2026-11-17 — Phase 2 gate passed on GitHub Actions (CI 43873830195, E2E 43873830255) before Phase 3 work started.
- 2026-11-17 — Every task belongs to a lead and has a due date-time and an assignee, so every open task is a next step. `Task.assigneeId` is nullable only so deleting a sample rep's account cannot fail; the API always requires one.
- 2026-11-17 — A Sales Rep gives tasks only to themselves. A task given to a Sales Rep must be on a lead that rep can see, so My day never links to a lead the rep cannot open.
- 2026-11-17 — "Tasks: Rep (own)" reads as: without `leadId` a Sales Rep lists only tasks assigned to them; with `leadId` they see every task on a lead they can see, and change only their own.
- 2026-11-17 — A touch is logged on `POST …/leads/:id/activities` with `type: TOUCH` and a channel (call, email, WhatsApp, meeting). Its next step travels in the same request and is created in the same transaction, so "a new open task" means one created with the touch; an older open task does not satisfy TASK-02. Closing as Won or Lost uses `close` in the same request, with the PIPE-03 rules.
- 2026-11-17 — The next-step rule is the org setting `nextStepRule` (`require` by default, or `warn`). In warn mode the touch saves, the response carries `warning: NEXT_STEP_MISSING`, and the timeline entry records it.
- 2026-11-17 — A touch restarts the stage SLA clock like a note. Creating or completing a task does not: setting a date is not following up.
- 2026-11-17 — Stuck is evaluated live from two stored deadlines, `Lead.slaDueAt` and `Lead.nextStepDueAt` (the earliest open next step, null for closed or archived leads), so the stuck filter never lags. The radar stores `Lead.stuckAt` and writes one STUCK timeline entry each time a lead becomes stuck; it runs inside every change to a lead or its tasks and every 5 minutes over all organizations. One SQL routine in `packages/db/src/radar.ts` serves both.
- 2026-11-17 — Open tasks on a lead that closes or is archived stay as they are, but they are no longer next steps: they leave My day, the radar and reminders.
- 2026-11-17 — `Notification` holds in-app notifications and the delivery record of every reminder and digest (`channel` IN_APP or EMAIL, a unique `dedupeKey`, a status). No extra table: the reminder key of TASK-04 is the unique key. The notification centre lists only IN_APP rows.
- 2026-11-17 — Reminders are found by a scan every minute (not one delayed job per task), so rescheduling, completing or deleting a task needs no job bookkeeping, and a worker that was down catches up on its next run. A reminder is due when the step is due within the next 15 minutes and not yet due.
- 2026-11-17 — Exactly once: each email row is claimed (PENDING → SENDING) and committed before sending, then marked SENT. A row left SENDING by a crash is retried only with a provider that drops repeats of the same idempotency key (Resend, `Idempotency-Key` = the reminder key); with SMTP or console it is skipped as INTERRUPTED rather than risk a second copy.
- 2026-11-17 — Email reminders and the daily digest follow the plan table: Starter and up ("Email reminders"). On Free, reminders are in-app only. The plan config gains `features.emailReminders`.
- 2026-11-17 — Each member chooses reminder emails and the daily digest per workspace (Account page, stored in membership preferences); both default to on. In-app reminders are always on. `PUT …/me/preferences` now merges the sections it is sent, so saving filters cannot wipe reminder choices.
- 2026-11-17 — The digest goes out from 08:00 in the organization's timezone (a later run that day still sends it), lists overdue next steps, today's and the member's stuck leads, and is skipped when all three are empty. Its content is fixed when the row is written.
- 2026-11-17 — The daily email budget is one Redis counter per UTC day, shared by the API (verification and invitation emails, never held back) and the worker. When it is spent, waiting reminder and digest emails move to the next UTC day; digests are sent first in every run. A reminder that can no longer arrive before its step is due is skipped (TOO_LATE).
- 2026-11-17 — Sample reps get no reminders or digests. Open, assigned sample leads get next steps (some overdue) so the radar and My day have something to show; they go with "Delete sample data".
- 2026-11-17 — NOT-01 also carries the UF-4 "inviter notified" message as an in-app MEMBER_JOINED notification; the email stays.
- 2026-11-17 — The notification bell polls the unread count every 30 s while the tab is visible (NOT-02 says poll for now).
- 2026-11-17 — Due times are typed in the organization's timezone and stored in UTC.
- 2026-11-17 — The worker's job intervals are configuration (`RADAR_INTERVAL_SECONDS` = 300, `REMINDER_INTERVAL_SECONDS` = 60). The E2E stack runs them every few seconds.
- 2026-11-17 — Phase 3 gate passed on GitHub Actions (CI 44022095532, E2E 44022095570) before Phase 4 work started.
- 2026-11-17 — `packages/workflow` holds the catalogue, conditions, state machine, retry, loop-protection and round-robin rules with no dependencies. The Zod request schemas live in `packages/shared`, built from its constants, with a compile-time check that both describe the same definitions.
- 2026-11-17 — Saving a version of an active workflow makes it the running version at once (no separate publish step). Runs already queued finish on the version they started with.
- 2026-11-17 — The outbox publisher locks unpublished events with SKIP LOCKED, adds one BullMQ `dispatch` job per event (job id = event id) and marks them published in the same transaction. Dispatch inserts executions with ON CONFLICT DO NOTHING on (versionId, eventId), so a replayed event is dropped (WF-07). A failed dispatch job is retried by BullMQ.
- 2026-11-17 — Each action runs in its own transaction together with its step row (unique on executionId, stepIndex), so a committed step is never repeated. Emails and notifications also carry the key `wf:{executionId}:{stepIndex}`.
- 2026-11-17 — FAILED means an attempt failed and another is scheduled; DEAD means no more automatic attempts. Only ActionErrors of kind VALIDATION, PERMISSION or NOT_FOUND fail fast; anything else, database deadlocks included, is retried. Backoff starts at `WORKFLOW_RETRY_BASE_MS` (30 s), doubles, keeps between half and all of the delay (jitter) and is capped at 1 hour.
- 2026-11-17 — A running attempt renews its lease at every step. The sweep (every `WORKFLOW_SWEEP_SECONDS`) counts an attempt silent for `WORKFLOW_LEASE_SECONDS` as failed and retries it, and re-queues runs whose job was lost. The claim, not the job id, keeps a run from starting twice.
- 2026-11-17 — Pausing cancels QUEUED runs and FAILED runs waiting for a retry (WF-05). A manual retry (FAILED or DEAD) starts a fresh set of 5 attempts and skips steps that succeeded; it is refused (409) while the workflow is paused.
- 2026-11-17 — A DEAD run notifies the organization's Owners and Admins in-app (`WORKFLOW_DEAD`). Email for it waits for the notification preferences of Phase 6.
- 2026-11-17 — Conditions are checked against the lead as it is when the event is dispatched. For `task.deadline_reached`, "assignee" is the task's assignee; for lead events it is the lead's owner.
- 2026-11-17 — A person's change raises events at depth 0; an event raised by a workflow action is one deeper, with `causationId` = the run. Depth above 3, or an event caused by a run of the same workflow, records a SKIPPED run.
- 2026-11-17 — The monthly run cap counts runs that were not SKIPPED, on real (non-sample) events, in the UTC calendar month. Activating a workflow checks the active-workflow limit (402 `activeWorkflows`). Sample workflows and runs never count.
- 2026-11-17 — Workflows may move a lead only to an open stage: Won and Lost need the deal value or loss reason a person gives (PIPE-03). "Notify the owner", "Create a task" for the owner and "Email the owner" fail fast on a lead with no owner.
- 2026-11-17 — WF-04 "tags" needed a field: `Lead.tags`, lower-case and unique. Workflows add or remove them; the lead page shows them.
- 2026-11-17 — An email to a lead is a `Notification` row with no user and a `toAddress`, sent by the existing delivery run after digests and reminders, within the daily budget. Placeholders ({{lead.name}}, {{lead.company}}, {{owner.name}}, {{org.name}}) are filled when the action runs.
- 2026-11-17 — `task.deadline_reached` is raised by the reminder run, once per due time (`Task.deadlineEventAt`). Steps already overdue when the migration ran, or when a sample workspace is seeded, count as reported.
- 2026-11-17 — The 2 sample workflows (ORG-04) are "Proposal follow-up" (a lead moved to Proposal gets a task and the owner a note) and "Escalate missed next steps" (tag `overdue`, notify the owner). Sample workflows run on sample leads only and real ones on real leads only. "Delete sample data" removes the workflows before the leads, the lock order a running workflow uses, and is retried once on a deadlock.
- 2026-11-17 — The API queues a manual retry on BullMQ itself (so it starts at once); if Redis is down the run stays QUEUED and the sweep picks it up.
- 2026-11-17 — The kill-the-worker test (NFR-REL-01) runs the production worker build as a child process, kills it with SIGKILL while runs are in progress, starts another, and checks that every run succeeds with each side effect exactly once.
