# Phase 4 — Workflow engine

## What gets built

- **`packages/workflow` (pure, no framework imports, ≥ 80% line coverage):** the catalogue (4 triggers, 4 condition fields with `is`, `is any of`, `is none of`, 5 actions), definition checks, condition evaluation, the execution state machine `QUEUED → RUNNING → SUCCEEDED | SKIPPED | CANCELLED | FAILED → (retry) → DEAD`, retry decisions with exponential backoff and jitter, loop protection (depth ≤ 3, no self-triggering, monthly execution cap by plan), round-robin choice and the idempotency keys.
- **Data:** `Workflow` (name, status DRAFT / ACTIVE / PAUSED, active version, round-robin cursor, `isSample`), `WorkflowVersion` (immutable: a database trigger refuses updates), `WorkflowExecution` (unique per version and event), `WorkflowExecutionStep` (unique per execution and step). `Lead.tags` for the "update tags" action. `Task.deadlineEventAt` so each deadline raises one `task.deadline_reached` event. `Notification` can carry an address for emails to a lead. RLS on every new table.
- **API (Manager and up):** `GET/POST …/workflows`, `GET …/workflows/:id`, `POST …/workflows/:id/versions`, `POST …/workflows/:id/(activate|pause)`, `GET …/executions`, `GET …/executions/:id`, `POST …/executions/:id/retry`. Activating checks the plan's active-workflow limit (402 with the limit name). Workflow changes and manual retries are audit-logged.
- **Worker:**
  - **Outbox publisher**, every second: unpublished `OutboxEvent` rows become BullMQ jobs (job id = event id), then are marked published.
  - **Dispatcher**: for each event, every active workflow on that trigger gets one execution row (unique on version and event, so a replay is dropped), then loop protection and conditions decide SKIPPED or QUEUED.
  - **Runner**: claims a run, executes the actions in order, each in its own transaction together with its step row, so a step that committed is never repeated. Retryable errors retry up to 5 attempts with backoff and jitter; validation and permission errors fail fast. After the last attempt the run is DEAD and Owners and Admins get an in-app notification.
  - **Sweep**, every minute: re-queues runs whose worker died mid-run (lease expired), and due retries that lost their job.
  - The reminder run also raises `task.deadline_reached` for next steps that just came due.
- **Actions:** assign (a user, or round-robin over chosen members), create task, schedule email to the lead or the owner (up to 30 days ahead, through the existing delivery and daily budget), internal notification, update priority, stage (open stages), owner or tags. Changes show on the timeline as "Workflow: name" and raise their own events with depth + 1.
- **Web:** Workflows list, builder (one trigger, AND-ed conditions, up to 10 ordered actions; saving creates a version), activate / pause / resume, version history, execution log with filters, run detail with step results and errors, and Retry for FAILED or DEAD runs. Workflow notifications in the notification centre; tags and workflow actions on the lead page.
- **Sample workspace:** the 2 sample workflows of ORG-04, active on sample leads only, removed with "Delete sample data".

## Requirements covered

WF-01 to WF-09, plus the 2 sample workflows deferred from ORG-04.
